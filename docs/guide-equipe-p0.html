Ce qui a été construit au P0

Guide d'apprentissage pour l'équipe : l'architecture retenue et ses raisons, les technologies, le chemin exact d'une note de service de la rédaction à la vérification publique, les tests qui le prouvent, et ce qui reste pour le P1.

État au 2 novembre 2026, branche feature/p0-socle-auth. Référence : cahier des charges EACT-CDC-001 v1.1. Chaque exigence citée ici (BF-xx, RG-xx, ENF-xx, TF-xx) renvoie à ce document.

Le fil rouge fonctionne de bout en bout. Une rédactrice écrit une note de service, la cheffe de service, le directeur et le Secrétaire Général la visent, le SG la signe avec son code à 6 chiffres, elle reçoit la référence N° 26/0001/NS/MINESUP/SG/DAG, un PDF/A avec QR code est produit, et n'importe qui peut vérifier son authenticité en scannant le QR, sans compte. Chaque action est inscrite dans un journal infalsifiable.

Ce que le P0 ne fait pas encore. Après la signature, l'acte reste à l'état « Signé ». La diffusion aux destinataires, la publication, le passage à « Exécutoire » et l'archivage relèvent des priorités suivantes (M07, M09). La recherche plein texte (M08) aussi. Voir Ce qui vient ensuite.

L'architecture et pourquoi

EACT est une application web 3-tiers : présentation (Next.js), logique métier (NestJS), données (PostgreSQL). Le serveur est un monolithe modulaire : un seul programme, découpé en 15 modules qui correspondent aux modules fonctionnels M01 à M15 du cahier des charges (§11, ADR 0001).

Sommes-nous en microservices ? Non, et c'est voulu

Le cahier des charges a évalué les microservices et les a écartés pour la V1 : pour une équipe de sept étudiants en douze semaines, déployer, tester et superviser une dizaine de services séparés coûterait plus que ce qu'ils apportent. Le découpage en modules prépare une éventuelle extraction : chaque module expose une interface et communique par des événements, jamais en lisant les tables d'un autre module pour son propre compte.

Conteneurs et réseau

Le déploiement suit la vue de déploiement du cahier des charges (§15) : seul nginx est exposé ; les données vivent dans un réseau interne sans accès à Internet (ADR 0006). La même architecture tourne sur un PC avec docker compose up -d.

Deux façons de lancer le même code : la démo complète (tout en conteneurs, derrière nginx, http://localhost:8080) et le mode léger pour développer (seuls PostgreSQL, Redis et Mailpit dans Docker ; API et web sur le poste avec rechargement à chaud, http://localhost:3001). En mode léger, l'antivirus est simulé et les fichiers sont sur disque ; le code métier ne change pas, seuls les adaptateurs changent (interfaces Stockage et Antivirus).

Deux règles à respecter quand vous ajoutez du code. Dans l'API, un module n'importe d'un autre que son service exporté ou ses événements. Dans le web, une Vue n'appelle jamais l'API : elle reçoit tout de sa Vue-Modèle.

Les transitions de statut autorisées sont écrites une seule fois, dans packages/shared/src/acte-statut.ts, et partagées par le serveur (qui refuse toute autre transition) et l'interface (qui n'affiche que les actions possibles).

Le parcours d'une note de service

Suivons une note de service rédigée par Christelle EBOGO (Service du Personnel). À chaque étape : qui agit, l'écran, l'appel à l'API, ce que fait le serveur, ce qui change en base, et les règles du cahier des charges appliquées.

1Se connecter

Qui, quel écran
Tout agent · /connexion (maquettes B1 à B5)
Appels
POST /v1/auth/login puis, pour les signataires, le SG et l'administrateur, POST /v1/auth/mfa/verify avec le code à 6 chiffres
Le serveur
Vérifie le mot de passe haché en Argon2id, compte les échecs (5 → verrou de 15 min), ouvre une session et pose deux cookies httpOnly : un jeton d'accès de 15 min et un jeton de rafraîchissement, renouvelé à chaque usage et refusé après 30 min d'inactivité.

session_utilisateur (empreinte du jeton, jamais le jeton), evenement_audit

Mécanismes clés

Ce sont les notions du cours de systèmes répartis (CDC §16) appliquées dans le code. À maîtriser pour la soutenance.

Verrou optimiste : pas de visa sur une version périmée

Chaque acte porte un numéro de version. Le client renvoie celle qu'il a lue ; la mise à jour s'écrit UPDATE … WHERE id = ? AND version = ?. Si quelqu'un a modifié l'acte entre-temps, aucune ligne n'est touchée et le serveur répond 409 : l'écran propose de recharger. Utilisé pour l'enregistrement automatique, la soumission et les visas. Sémantique « au plus une fois ».

Séquenceur : un numéro unique, sans trou

Deux signatures simultanées du même type et de la même structure ne doivent jamais recevoir le même numéro. La ligne du compteur est verrouillée par SELECT … FOR UPDATE dans la transaction de signature : la seconde attend la première. Si la transaction échoue, l'incrément est annulé avec elle, donc pas de trou. Prouvé par TF-07 : 20 signatures lancées en même temps donnent 20 numéros consécutifs. (ADR 0003, CDC §16.4)

Idempotence : exactement une fois

Le navigateur génère une clé unique par tentative de signature et l'envoie dans l'en-tête Idempotency-Key. Si la requête est rejouée (double clic, coupure réseau), le serveur retrouve la clé et renvoie le résultat déjà obtenu, sans attribuer de second numéro. Prouvé par TF-08.

Journal chaîné

Chaque entrée stocke l'empreinte SHA-256 de son contenu et celle de l'entrée précédente. Un trigger PostgreSQL refuse UPDATE, DELETE et TRUNCATE. La vérification recalcule toute la chaîne. Les écritures sont sérialisées par un verrou consultatif PostgreSQL pour garder l'ordre. (ADR 0004)

Invocation implicite

Les services publient des événements (acte.soumis, acte.vise, acte.signe…). Le journal d'audit écoute tout, les notifications écoutent ce qui les concerne. Ajouter un réacteur ne touche pas au circuit. Quand l'audit doit être atomique avec l'action (soumission, visa, signature), il est écrit dans la même transaction.

Session sans état et délégations

Le jeton d'accès est un JWT signé de 15 min qui porte l'identité et les rôles : n'importe quelle instance de l'API peut le vérifier sans base de sessions partagée (redondance active, CDC §16.2). Le jeton de rafraîchissement, lui, est en base pour pouvoir être révoqué. Les délégations sont lues à chaque vérification de compétence, avec leurs dates : une délégation échue cesse d'agir sans attendre la tâche qui la désactive.

Tests et procédures

La procédure suivie à chaque module

  1. Relire l'exigence du cahier des charges et la maquette de l'écran.
  2. Modifier le schéma par une migration Prisma versionnée, jamais à la main.
  3. Écrire l'API, puis l'interface ; vérifier les types (tsc) des deux côtés.
  4. Écrire et faire passer une recette de bout en bout qui joue les parcours réels, chaque contrôle citant son exigence.
  5. Lint, tests unitaires, builds de production de l'API et du web.
  6. Commit au format Conventional Commits (feat(m05): …), message qui explique le pourquoi ; rien n'est poussé sans décision de l'équipe.
